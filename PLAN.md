## 1. Суть

Настольная программа для ведения семейного бюджета, которая заменяет семейную таблицу Excel
(её структура воспроизведена в `tools/fixtures/make_workbook.py`). Программа
воспроизводит её структуру и логику, но хранит данные в зашифрованном переносимом файле
и считает всё сама, без ломающихся формул.

Три главных свойства:

1. **Знакомый интерфейс.** Экран месяца выглядит как лист его таблицы: те же колонки в том же
   порядке, итоги по категориям сверху, блоки по картам и продуктам справа, вкладки по месяцам,
   лист «Свод» за год. Переучиваться не нужно.
2. **Карты и кэшбэк — центр системы.** У семьи 30–50 карт двух участников с разными
   кэшбэк-категориями и лимитами, меняющимися каждый месяц; плюс кредитки с грейс-периодами и
   накопительные счета с промо-окнами. Программа ведёт реестр продуктов, считает кэшбэк и
   остатки лимитов, показывает сроки.
3. **Данные — один зашифрованный файл на семью.** Открывается на любом компьютере с программой
   и паролем. Никакого сервера, никаких аккаунтов.

## 2. Принятые решения

| # | Решение | Почему |
|---|---------|--------|
| D1 | **Tauri 2 + Rust-ядро + веб-UI**. | Маленький бинарник; вся финансовая логика на Rust с тестами; то же ядро потом пойдёт в Android-библиотеку. |
| D2 | **Сборки только под Windows** (пользователи на Windows), разработка на Mac, сборка в GitHub Actions. | Приватный репозиторий; macOS-сборка не нужна для пользователей. |
| D3 | Хранение — **один файл SQLite, зашифрованный SQLCipher**, пароль на открытие. | Транзакции, целостность, быстрые отчёты; файл копируется на флешку. |
| D4 | **Участники** — список, не пара: сейчас двое, любое число потом. | Чтобы программа подошла любой семье. |
| D5 | **Продукты банков** (грейсы кредиток, промо-окна накопительных счетов, сроки) — **в MVP**, а не потом. | Выбор автора: это ежедневный инструмент пользователя. |
| D6 | **Подсказка «какой картой платить»** — в MVP, но как **отключаемая функция**; работает только если на текущий месяц введены правила кэшбэка. | Выбор автора. |
| D7 | Кэшбэк по операции — **сумма в копейках**; процент показывается как производная. Вводить можно и %, и сумму. | В исходной таблице есть оба случая (6% → 134 ₽; сертификат 666 ₽ → 200 ₽ кэшбэка). |
| D8 | Остатки лимитов кэшбэка считаются **из журнала операций + ручная корректировка**. | Пользователь сейчас сверяется с приложениями банков вручную; не все траты могут попасть в журнал. |
| D9 | Деньги — **целые копейки (`i64`)**, одна валюта (RUB) в MVP. Никаких float. | Точность. |
| D10 | Импорт его xlsx и **экспорт в xlsx той же структуры** — в MVP. | Снимает страх миграции: в любой момент можно вернуться в Excel. |
| D11 | При проектировании дизайна UI использовать скилл **`frontend-design`**. | Требование автора. |
| D12 | **React 18.3 + Glide Data Grid 6.0.3** (стабильная пара). Переход на React 19 — когда выйдет стабильная Glide 6.0.4. Glide 6.0.3 пропатчен (`patches/`, `pnpm patch`): ввод кириллицы в выделенную ячейку — перенос исправления из 6.0.4-alpha, и русские надписи окна поиска (`Ctrl+F`); при обновлении Glide патч пересмотреть. | Glide 6.0.3 официально поддерживает React ≤18; React 19 — только в alpha. AG Grid Community не умеет вставку диапазонов (Enterprise). Без патча Glide 6.0.3 начинает правку по нажатию только для ASCII — русский текст не вводился бы «как в Excel». Решено 2026-10-27. |
| D13 | **Округление кэшбэка — настройка каждого продукта** (`product.cashback_rounding`), см. §6. По умолчанию — вниз до рубля, как в исходной таблице (`ROUNDDOWN(G*H;0)`). | У разных банков разные правила. Решено 2026-10-27. |
| D14 | Основная ветка репозитория — **`master`** (CI и правила ссылаются на неё). | Решено 2026-10-27. |
| D15 | SQLCipher: на Windows — `bundled-sqlcipher-vendored-openssl` (OpenSSL собирается из исходников и линкуется статически), на macOS — `bundled-sqlcipher` с CommonCrypto, на Linux (только CI) — с системным OpenSSL. | Без OpenSSL на Windows `bundled-sqlcipher` не собирается. |
| D16 | **Строка 3 листа месяца** — квартплата/ипотека: «квартиры», регулярная, без кэшбэка (поэтому категории в формулах считаются со строки 4, а «Ср. %» — без G3). Импорт читает её как обычную операцию. | Подтверждено автором 2026-10-27. |
| D17 | **Неизвестная категория, участник или карта при вводе** добавляются в справочник автоматически; внизу экрана сообщение «Добавлена …», Ctrl+Z отменяет вместе с правкой. | Так работает вставка из Excel. Решено 2026-10-27. |
| D18 | **Таблицы этапов 2–3** (правила кэшбэка, MCC, транши, погашения, поступления, план дохода, условия продуктов, сроки) появляются миграциями в своих этапах, а не пустыми на этапе 1. Таблица операций в базе называется `entry` (`transaction` — ключевое слово SQL). | Нет непроверенных таблиц в схеме. Решено 2026-10-27. |
| D19 | **«Ср. %» = кэшбэк / (Итого − строки с отметкой «Не в Ср. %»)**. Отметка — у регулярного платежа (D37), не у категории. | Квартплата кэшбэка не даёт и в базу не входит. Решено 2026-10-27, уточнено D37. |
| D20 | **MCC — после MVP.** Правила кэшбэка бывают «по категории» и «на всё»; таблицы `mcc_code` и поля `cashback_rule.mcc_code` нет. | В журнале (§5) и в исходной таблице MCC нет — сопоставлять не с чем. Решено 2026-10-27. |
| D21 | **Траты правила:** у правила категории — операции этой картой в этой категории за месяц; у «на всё» — операции этой картой, у категории которых нет своего правила на этой карте. Лимиты расходуются в порядке строк журнала; корректировка (D8) — траты вне журнала, кэшбэк с них считается по ставке правила. Кэшбэк «по правилу» пересчитывается при любом изменении месяца; ручной (% или сумма) не меняется, но лимит занимает. | Как считает банк: что раньше потрачено, то раньше и съело лимит. Решено 2026-10-27. |
| D22 | **Блок «Итого кэшбэк / Ср. %»** — справа, первым, как ячейки L7:M8 исходной таблицы; из полосы итогов над журналом убран. | В шапке листа исходной таблицы кэшбэка нет. Решено 2026-10-27. |
| D23 | **Приёмка этапа 2** — на синтетическом месяце с остатками, посчитанными вручную; сверка с реальными правилами — когда они появятся. | Правые блоки образца пустые. Решено 2026-10-27. |
| D24 | **Этап 3 делится на три части**: 3a — продукты и сроки, 3b — поступления, план дохода и «Свод», 3c — экспорт xlsx/json. У каждой части свой PR. | Этап большой; так каждая часть проверяется отдельно. Решено 2026-10-27. |
| D25 | **Импорт правых блоков (§9 п. 3) отложен** до реального файла или примера этих блоков (`docs/backlog.md`). | В образце правые блоки пустые — распознавать нечего. Решено 2026-10-27. |
| D26 | **«Общий % кешбека» в «Своде»** = кэшбэк / сумма месяца, как в его формуле `V/D` (без вычета квартплаты, в отличие от «Ср. %» месяца). | Совпадение с его листом. Решено 2026-10-27. |
| D27 | **Погашение вносится в конкретный транш**; по умолчанию предлагается незакрытый транш с ближайшим окончанием. Распределение одного платежа по нескольким траншам — позже, по реальным данным. | Решено 2026-10-27. |
| D28 | **Хранится только то, что нельзя вычислить**: у операции `grace_period_id` — только ручная привязка (пусто = автопривязка по дате); статус транша (активен / погашен / просрочен) вычисляется; в `deadline` — только пользовательские напоминания, сроки грейсов и открытия НС считаются из траншей и условий. Операция без даты к траншу не привязывается. | Нет рассинхронизации: новый транш сразу забирает свои покупки. Решено 2026-10-27. |
| D29 | **Экспорт xlsx — значения, не формулы.** Листы как у него: «Служебный», месяцы `MM.YY` (журнал в A–J с 3-й строки, итоги в строках 1–2 по его объединённым колонкам — группам, «Итого:» / «Ср. %» в L7:M8), «Свод» по годам. У строк с кэшбэком по правилу пишется только сумма кэшбэка (без %), иначе повторный импорт пересчитал бы её без лимитов. Выгрузка читается нашим импортом обратно в тот же журнал. | Снимок и путь назад в Excel, точно совпадающий с программой. Решено 2026-10-27. |
| D30 | **Данные, которых нет в его книге** (категории с группами, карты с условиями, регулярные платежи, правила кэшбэка, поступления, план дохода, грейсы, погашения, напоминания), идут в xlsx отдельными листами после «Свода». | При экспорте ничего не теряется. Решено 2026-10-27. |
| D31 | **Экспорт json** — все хранимые данные файла (без вычисляемых итогов и без истории изменений) с названием и версией формата. xlsx и json не зашифрованы: перед сохранением — предупреждение. | Резервная копия в открытом формате. Решено 2026-10-27. |
| D32 | **Копии файла.** При открытии, не чаще раза в день, файл копируется как есть (зашифрованный, тем же паролем) в папку «<имя> — копии» рядом с ним: `<имя> ГГГГ-ММ-ДД.reestr`; хранятся 10 последних. Копия делается до обновления схемы. Файл, открытый из папки копий, копий не делает. Если копия не получилась, файл всё равно открывается, а внизу экрана сообщение. | Защита от ошибок и порчи файла без облака и сети. Решено 2026-10-28. |
| D33 | **Смена пароля** на странице «О файле и пароле»: текущий пароль, новый дважды, снова предупреждение, что пароль не восстановить. Текущий проверяется на временной копии файла, затем `PRAGMA rekey`. Старые копии открываются старым паролем — это сказано на странице. | Решено 2026-10-28. |
| D34 | **Настройки вида** (размер шрифта таблиц, какие блоки справа и в каком порядке) хранятся на компьютере, а не в файле. | Размер шрифта зависит от экрана. Решено 2026-10-28. |
| D35 | **Первый выпуск — 0.1.0**, тег `v0.1.0` (или ручной запуск сборки с полем «release») запускает сборку под Windows и после успешной сборки публикует выпуск с установщиками в Releases. Установщик без цифровой подписи; README объясняет предупреждение SmartScreen. | Решено 2026-10-28. |
| D36 | **CI и сборки — только на крупных изменениях.** Мелкие правки копятся в рабочей ветке без PR и перед каждой отправкой проверяются локально (`cargo test`, `clippy`, `fmt`, `pnpm check`). PR в `master` — а с ним прогон `ci.yml` — открывается, когда готово крупное изменение; на push в `master`, черновые PR и правки только документации CI не запускается. Сборки под Windows и выпуски — только по команде автора. | Экономия минут GitHub Actions. Решено 2026-10-28. |
| D37 | **Вне базы «Ср. %» — только квартплата.** Отметка «Не в Ср. %» стоит у регулярного платежа «Квартплата»; строки журнала с тем же наименованием (без учёта регистра) не входят в базу. В новых файлах платёж «Квартплата» есть сразу. Импорт ставит отметку платежу с наименованием строки 3 каждого листа (D16) или создаёт такой платёж. Старые файлы при открытии переносят отметку с категории на платёж «Квартплата». | Как в его формуле `M7/(H2−G3)`: интернет и прочие траты «квартир» в базе остаются. Решено автором 2026-10-28. |
| D38 | **Android — Tauri 2**, то же ядро и хранилище на Rust, тот же шифрованный файл; свой маленький интерфейс телефона вместо таблицы. Пока — один телефон пользователя (Android 15–16): APK только под `arm64-v8a`. APK подписан своим ключом (ключ — в секретах репозитория), выпускается в Releases без Google Play; сборка — отдельным workflow вручную или по тегу, как Windows (D36). | Одна кодовая база; эмуляторов нет — проверка на телефоне. Решено автором 2026-10-28. |
| D39 | **Обмен с телефоном — вариант А: компьютер главный, телефон только добавляет строки.** Программа в сеть не ходит; файлы лежат в папке Яндекс Диска, которую синхронизирует его приложение. Компьютер пишет туда «<файл> — для телефона.reestr» (копию основного файла), телефон — «<файл> — с телефона.reestr» (свой файл). Строка с телефона получает постоянный ключ и номер версии; «Забрать с телефона» на компьютере добавляет новые строки и переносит правки и удаления строк, которые на компьютере не трогали. Если строку меняли и там и там, остаётся версия компьютера. Компьютер помнит, что забрал, поэтому удалённая на нём строка с телефона не вернётся, а повторный перенос ничего не задвоит. Справочники приходят на телефон с новой копией; назначение, участник и карта переносятся названиями (новое название создаётся, как при вводе, D17); кэшбэк строки с телефона считает компьютер по своим правилам. | Конфликтов правок нет по построению; Яндекс Диск у пользователя есть. Решено автором 2026-10-28. |
| D40 | **Телефон в первой версии:** ввод строки, подсказка карты (D6) с остатками лимитов, строки месяца. Править и удалять можно только свои строки, которые компьютер ещё не забрал (до прихода новой копии). Правила, справочники, «Продукты», «Свод», импорт и экспорт — только на компьютере. | Решено автором 2026-10-28. |

## 3. Не-цели MVP

- Android-приложение (после MVP; ядро готовится к этому с первого дня — см. §4.2).
- Синхронизация, облако, аккаунты, любой сервер.
- Импорт банковских выписок (CSV/XLSX из банков) и автокатегоризация.
- Калькулятор «кэшбэк vs проценты по накопительному» (есть в исходной таблице; после MVP).
- Несколько валют, инвестиции, кредиты как сущность (кроме грейса кредиток).
- Подпись кода сертификатом (платно); SmartScreen будет предупреждать при первом запуске —
  описать в README, как запустить.

## 4. Архитектура

### 4.1. Стек

| Слой | Выбор | Примечание |
|------|-------|------------|
| Оболочка | Tauri 2 | Windows использует WebView2 (встроен в Win10/11). |
| Ядро | Rust: `rusqlite` (feature `bundled-sqlcipher`), `serde`, `rust_decimal` **не** нужен (копейки в `i64`), `time`/`chrono` | Вся бизнес-логика — чистые функции в crate `core`, без Tauri и без SQL. |
| Шифрование | SQLCipher 4 (AES-256, PBKDF2-HMAC-SHA512, 256k итераций по умолчанию) | Проверить актуальные дефолты. Argon2id поверх — только если замеры покажут, что нужно. |
| UI | React 18.3 + TypeScript (strict) + Vite | Выбор React из-за грид-компоненты; версия — D12. |
| Таблица | Glide Data Grid 6.0.3 (MIT, canvas, Excel-подобное редактирование, копирование диапазонов) | API сверено 2026-10-27. AG Grid Community не подходит как запасной: вставка диапазонов только в Enterprise. |
| Стили | CSS Modules + CSS custom properties, без UI-библиотек | Дизайн делается по скиллу `frontend-design`. |
| Экспорт/импорт xlsx | Rust: `calamine` (чтение), `rust_xlsxwriter` (запись) | В ядре, не в UI. |
| Тесты | Rust: `cargo test` (логика кэшбэка, грейсов, импорта); UI: Vitest; e2e — Playwright через `tauri-driver` (если стабильно на Windows CI, иначе отложить) | |
| CI | GitHub Actions: `windows-latest` → `.msi` + `.exe` (NSIS) в Releases | Лимит минут приватного репозитория ограничен (у автора ~3000 мин/мес; Windows-минуты считаются ×2 — сверить). Бюджет CI описан в §16. |

### 4.2. Слои и правило зависимостей

```
reestr/
├── crates/
│   ├── core/        # domain model, cashback engine, grace/savings logic, reports, xlsx import/export
│   ├── storage/     # SQLite schema, migrations, encrypted open/create, snapshots
│   └── app/         # Tauri commands: thin glue between UI and core/storage
├── ui/              # React app
```

Правило: `core` не знает ни о SQLite, ни о Tauri. `storage` знает о SQLite, не о Tauri.
`app` — только команды и сериализация. Так ядро позже компилируется в Android-библиотеку без переделок.

### 4.3. Файл данных

- Расширение: `.reestr`. Внутри — база SQLCipher.
- Открытие: пароль → SQLCipher. **Пароль не восстанавливается**, это написано на экране создания
  файла крупно. Предлагать записать пароль на бумагу.
- Автосохранение: каждое изменение — транзакция, кнопки «Сохранить» нет.
- **Снапшоты**: `<name>.snapshots/<name>-YYYY-MM-DD-HHMM.reestr` — автоматически при закрытии
  месяца и по кнопке; хранить последние N (настройка, по умолчанию 20). Снапшот — тот же
  зашифрованный файл.
- **История изменений**: таблица `change_log` (что, когда, старое/новое значение) — даёт undo
  в пределах сеанса и «что я менял».
- Экспорт: `.xlsx` в структуре исходной таблицы (§8) и `.json` (полный дамп для миграций).
- Таблица `meta`: версия схемы, дата создания, список участников. Миграции схемы — в `storage`.

## 5. Модель данных

Все суммы — копейки `i64`. Даты — ISO `YYYY-MM-DD`. Месяц — `YYYY-MM`.

```
participant      id, name, sort_order, is_active
bank             id, name, short_name
product          id, bank_id, participant_id, kind (debit|credit|savings|deposit|cash),
                 short_name  ("Газпром КР", "ПСБ 3170" — как в таблице), full_name,
                 cashback_rounding (floor_rub|floor_kop|half_up_rub|half_up_kop; default floor_rub, D13),
                 is_active, opened_at, closed_at, notes

                 -- user-facing categories exactly as the user names them ("еда", "продукты", …)

                 -- a category belongs to at most one group; ungrouped categories report as themselves

                 is_regular, notes, created_at, updated_at
```

Вычисляемое (не хранится):
- итоги месяца по категориям и «Регулярные»;
- `rule.spent = Σ transaction.amount по product+category+month + spent_adjustment`;
  `rule.remaining_spend = spend_cap − spent`; `rule.remaining_cashback`;
- `grace_period.debt = Σ transaction.amount с этим grace_period_id + debt_adjustment`;
  `grace_period.remaining = debt − Σ repayment.amount`; `days_left = end_date − today`;
  `product.total_debt = Σ remaining по активным траншам`;
- `savings.can_reopen_at = promo_closed_at + reopen_after_days`;
- «Свод»: по месяцам сумма трат, план дохода, баланс, % кэшбэка, прирост к прошлому году.

## 6. Логика кэшбэка

1. При вводе операции, когда заданы продукт + категория + месяц, ядро ищет правило:
   точное (категория) → MCC → «на всё». Если найдено и лимит не исчерпан — подставляет
   `cashback_amount = round(amount × rate, product.cashback_rounding)`, с учётом остатка
   `cashback_cap`. Режим округления задаётся на карточке продукта (D13): вниз до рубля
   (по умолчанию, как в исходной таблице), вниз до копейки, математически до рубля, математически до копейки.
2. Пользователь может перебить: ввести % или сумму. `cashback_source` фиксирует, откуда число.
3. Изменение правила задним числом **не** пересчитывает операции с `manual_*`; с `rule` —
   пересчитывает, спросив подтверждение. Ответ «оставить как есть» превращает их кэшбэк
   в ручной. Пустой кэшбэк с подходящим правилом заполняется тоже только с подтверждением.
4. **Подсказка карты (D6).** Настройка `card_suggestions.enabled` (выкл. по умолчанию до
   первого ввода правил). Если включена и выбрана категория — рядом с полем «карта»
   показывается список продуктов с правилом на этот месяц, отсортированный по
   `rate` с учётом остатка лимита; продукты с исчерпанным лимитом — внизу, серым.
   Если на месяц правил нет — подсказка молчит, без предупреждений.
5. Правила на новый месяц: кнопка «Скопировать правила из прошлого месяца» + правка.
   Это ровно то, что пользователь сейчас делает при создании листа.
6. Все расчёты — функции в `core::cashback` с тестами на граничные случаи: лимит исчерпан
   частично, копейки, нулевая ставка, правило «на всё» рядом с категорийным, каждый режим
   округления.

## 7. Банковские продукты и сроки

- **Экран «Продукты»**: таблица всех продуктов, фильтр по участнику/банку/типу/активности;
  карточка продукта с условиями.
- **Кредитки — модель траншей.** У каждого банка свои правила грейса, поэтому программа их
  **не вычисляет**: пользователь вводит даты начала и окончания каждого грейс-периода
  (транша). По одной карте одновременно может быть несколько активных траншей с
  перекрывающимися сроками (например, грейс 120 дней, новый открывается каждый месяц —
  одновременно живут 4). Правила:
  - операция по кредитке автоматически привязывается к траншу, который начался позже всех
    на дату покупки или до неё; привязку можно изменить вручную;
  - долг транша = сумма привязанных операций + ручная корректировка; погашения — отдельные
    записи с датой и суммой; остаток = долг − погашено;
  - кнопка «Начался новый грейс» создаёт транш с датами по умолчанию
    (`default_grace_days` как подсказка), даты правятся;
  - статус `overdue` ставится автоматически, если `end_date < today` и остаток > 0.
  Экран показывает по каждой карте список активных траншей: срок, дней осталось, остаток;
  и общий долг по всем кредиткам. Цветовая индикация ≤7 дней и просрочка.
- **Накопительные счета**: «закрыт», «можно открыть с», «нет НС/вкладов 90+ дней» как флаг
  условия. Список «что можно открыть сейчас».
- **Панель «Сроки»** (правая часть экрана месяца и отдельный экран): ближайшие окончания
  траншей, открытия НС, пользовательские напоминания. **Уведомления только внутри
  программы** (счётчик на вкладке «Сроки» + список при запуске); системные уведомления — не в MVP.
- Остатки лимитов/балансов по кредиткам — вводятся вручную (как сейчас), с датой актуальности.

## 8. Интерфейс — «как в его Excel»

Принцип: **структура и порядок — как в исходной таблице; качество исполнения — современное**
(читаемость, фокус, клавиатура). Никаких «умных» переосмыслений раскладки. Дизайн-система
создаётся по скиллу `frontend-design`, но сдержанная: таблица — главный элемент, акцентных
цветов минимум, цвета — только для статусов (срок близко, лимит исчерпан).

**Главный экран — месяц.** Вкладки месяцев `MM.YY` как листы. Лист месяца:
- слева — журнал: колонки в том же порядке: `№ | Наименование | Назначение | Регулярная | Участник | Дата | Сумма | % | Кэшбэк | Карта`;
- над журналом — строка итогов по категориям (как в его шапке) + «Регулярные»;
- справа — блоки, как у него: «Итого кэшбэк / Ср. %», «Регулярные платежи» (шаблоны),
  «Лимиты по картам» (правила месяца с остатками), «Кредитки / грейс», «Накопительные счета»,
  «Приход / расход / дельта»;
- блоки сворачиваются; состав и порядок блоков — настройка.

**Ввод.** Enter/Tab по ячейкам, стрелки, `Ctrl+Z`, вставка из буфера, автодополнение
«Наименования» по истории с подстановкой категории, участника, карты и флага «регулярная»
из последней такой же операции. Новая строка — всегда снизу, как в Excel. Удаление — с
подтверждением, восстановление через undo.

**Экран «Свод».** Таблица по годам и месяцам: сумма, план дохода, баланс, категории,
регулярные, кэшбэк, общий баланс, % кэшбэка; внизу — сумма, доля, среднее, средний прирост.
Отдельно — сравнение с прошлым годом.

**Экран «Справочники»** (его лист «Служебный»): категории с флагом «регулярная», участники,
банки, MCC.

**Категории и группы.** Пользователь вводит категории ровно так, как привык («еда», «продукты»,
«лечение», «лекарства»); в журнале, итогах месяца и в «Своде» по умолчанию показываются
именно они. Дополнительно категории можно объединить в **группы** («Здоровье» = лечение +
лекарства; «Внешность» = красота + косметика + одежда + обувь). Группы — необязательный
второй уровень: переключатель «по категориям / по группам» в итогах месяца и «Своде»,
отдельный блок «По группам» справа. Категория без группы показывается как есть.
Импорт из его xlsx создаёт группы по объединённым столбцам «Свода»
(«Лечение/лекарства», «Красота/косметика», «Одежда/обувь») — их можно переименовать или удалить.

**Экраны «Продукты», «Сроки», «Настройки»** — см. §7.

**Клавиатура и доступность:** `Ctrl+N` новая операция, `Ctrl+F` поиск по журналу,
`Ctrl+Tab` следующий месяц; контраст ≥ 4.5:1; минимальный размер шрифта таблицы — настройка
(пользователю может понадобиться крупнее).

## 9. Импорт и экспорт

**Импорт xlsx (мастер):**
1. Лист `Служебный` → категории (+ флаг регулярной).
2. Листы `MM.YY` → операции (колонки 1–7 + % + кэшбэк + карта). Названия карт → продукты
   (мастер показывает список найденных имён и просит указать банк, тип, участника;
   суффиксы `В`/`О` → участник, `КР`/`КК` → кредитная, предлагается автоматически).
3. Правые блоки (правила кэшбэка, грейсы, НС) — **полуавтоматически**: мастер показывает
   распознанные строки, пользователь подтверждает/правит. Не пытаться парсить всё — там
   свободная форма.
4. `Свод` — не импортируется, пересчитывается.
Импорт идемпотентен: повторный импорт того же файла не дублирует операции.

**Экспорт xlsx:** структура листов и колонок повторяет оригинал (Служебный + месяцы + Свод),
но с реальными числами вместо формул (D29); остальные данные — листами в конце (D30). Это
резервный путь назад в Excel. **Экспорт json** — все данные файла (D31).

## 10. Безопасность и приватность

- Ноль сетевых запросов. CSP в Tauri запрещает любые внешние источники. Запрещены зависимости,
  которые ходят в сеть (аналитика, автообновление с телеметрией). Автообновление — не в MVP.
- Файл зашифрован целиком; пароль в памяти только на время сеанса; при блокировке/закрытии —
  обнулять (`zeroize`).
- Снапшоты и экспорт xlsx — **xlsx не зашифрован**; при экспорте предупреждение.
- Буфер обмена: при копировании диапазонов из таблицы — обычный текст, без предупреждений
  (это ожидаемое поведение «как в Excel»).
- Логи приложения — без сумм и названий; только технические события.

## 11. Риски

| Риск | Что это значит | Что делаем |
|------|----------------|------------|
| Потеря пароля = потеря данных | Восстановления нет по построению. | Предупреждение при создании, предложение записать пароль; экспорт в xlsx как резерв. |
| Остатки лимитов врут, если не все траты в журнале | Пользователь не всё записывает в день покупки. | `spent_adjustment` (D8) + показ даты последней корректировки; подсказка карты помечена «по данным журнала». |
| Grid-компонента не даст «ощущения Excel» | Самая заметная для пользователя часть. | Этап 0 — прототип только таблицы с вводом; показать пользователю до всего остального. |
| Tauri на Windows из-под Mac | Сборку локально не проверить. | CI с первого коммита; тестовая машина — Windows-ноутбук пользователя, `.exe` из Releases. |
| SmartScreen | «Неизвестный издатель» при запуске. | Инструкция в README; сертификат — не в MVP. |
| Рост требований («а ещё бы…») | Исходная таблица показывает десятки нишевых блоков. | Всё, чего нет в §5, — в `docs/backlog.md`, не в код. |

Каждый этап — ветка и PR, заканчивается рабочим состоянием и короткой демонстрацией пользователю,

**Этап 5 — Android: ввод на ходу и подсказка карты** (D38–D40)
- 5a: обмен в ядре и хранилище (ключи и версии строк телефона, «Забрать с телефона», копия для
  телефона, перенос незабранных строк в новую копию на телефоне), на компьютере — папка обмена,
  кнопка «Забрать с телефона», запись копии для телефона. Всё проверяется тестами без Android.
- 5b: интерфейс телефона — ввод строки, «Какой картой платить», строки месяца; файлы через
  Яндекс Диск. Сделано: пользователь один раз выбирает в системном окне Android два файла на Диске
  («… — для телефона» и «… — с телефона»; второй компьютер кладёт пустым, чтобы его не
  создавать на Диске). Диалог Tauri на Android не сохраняет доступ к файлу после перезапуска,
  поэтому выбор и копирование делает свой плагин `crates/files` (`ACTION_OPEN_DOCUMENT` с
  постоянным доступом). Пароль спрашивается при каждом запуске и когда телефон отложили больше
  чем на 5 минут; при входе телефон берёт свежую копию, после каждой строки кладёт свой файл.
  Экраны проверяются в настольной сборке (`localStorage["reestr.phone"] = "1"`).
- 5c: сборка APK (`arm64-v8a`, своя подпись), workflow вручную и по тегу, инструкция для пользователя.
  Сделано: Android-проект в `crates/app/gen/android` (иконки из `icons/icon.png`, светлая тема,
  страница не уходит под системные панели и клавиатуру), OpenSSL для SQLCipher собирается из
  исходников и на Android, SQLite держит временные таблицы в памяти. Ключ подписи — у автора и в
  секретах `ANDROID_KEYSTORE`, `ANDROID_KEY_PASSWORD`; `android-build.yml` — вручную и по тегу.
  Разрешение `INTERNET` осталось из шаблона Tauri: WebView загружает страницы приложения по
  адресу `tauri.localhost`; сетевых запросов приложение не делает, CSP их запрещает. HTTP-клиент
  `reqwest` в зависимостях Tauri на Android нужен только режиму разработки (`cfg(dev)`).
- *Готово, когда:* строка, внесённая на телефоне, после «Забрать с телефона» стоит в журнале
  компьютера с кэшбэком по его правилам, а повторный обмен ничего не задваивает и не возвращает
  удалённое.

**После MVP (отдельные планы):** калькулятор «кэшбэк vs проценты», импорт банковских выписок,
несколько валют, синхронизация файла через выбранное пользователем хранилище.

## 15. Правила для Claude Code

- Перед каждым этапом — короткий план, после подтверждения — реализация.
- Не добавлять зависимости без необходимости; для каждой новой — одна строка «зачем» в PR.
  Запрещены зависимости с сетевой активностью (аналитика, автообновление, загрузчики).
- Деньги — только `i64` копейки; в UI форматирование в рубли. Любой `f64` для денег — баг.
- Бизнес-логика — в `crates/core` с тестами; UI не считает деньги.
- Раскладка экрана месяца повторяет исходную таблицу (§8); изменения порядка колонок/блоков —
  только по явному решению автора.
- Дизайн UI — по скиллу `frontend-design`; при этом таблица остаётся главным элементом,
  декоративность минимальная.
- Сверять API внешних библиотек (`tauri`, `glide-data-grid`, `rusqlite`/SQLCipher,
  `calamine`, `rust_xlsxwriter`) по актуальной документации, а не по памяти.
- Машина разработчика — MacBook Air M2, 8 ГБ: Windows-сборки только в CI; не запускать
  тяжёлые эмуляторы.
- Коммиты — на английском, Conventional Commits.

## 16. Рабочий процесс и бюджет CI

**Две фазы разработки.**

1. **Облако (сейчас).** Claude Code работает в облачной сессии, пока не сгорели Cloud Credits.
   В облаке: каркас, ядро (`core`, `storage`), импорт xlsx, UI-код, unit-тесты. Всё, что
   можно проверить без Windows и без окна приложения, проверяется там: `cargo test`,
   `cargo clippy`, `vitest`, `tsc`. Облачная сессия не запускает Tauri-окно — визуальная
   проверка идёт через `.exe` из CI на Windows-ноутбуке.
2. **Локально (потом).** Репозиторий клонируется на Mac автора; дальше — Claude Code в
   приложении. `cargo tauri dev` на Mac работает для разработки UI (macOS-окно), сборки для
   Windows — по-прежнему только CI.

Код не должен зависеть от того, где он пишется: никаких абсолютных путей, никаких
предположений об ОС в тестах (пути через `std::path`, временные файлы через `tempfile`).

**Бюджет GitHub Actions** — лимит минут в месяц ограничен (Windows ×2), поэтому:

- **Два отдельных workflow.**
  - `ci.yml` — `ubuntu-latest` (минуты ×1): `cargo test`, `cargo clippy`, `tsc`, `vitest`.
    Крейт приложения (`crates/app`, Tauri) тоже проверяется clippy — с системными пакетами
    WebKitGTK (решено 2026-10-27: ошибки ловятся на PR, а не на ручной Windows-сборке).
    Запускается на готовый (не черновой) PR в `master` и вручную (D14, D36); не на push,
    не на правки только документации.
  - `windows-build.yml` — `windows-latest` (минуты ×2): полная сборка Tauri `.exe`/`.msi`.
    **Только вручную** (`workflow_dispatch`) и по тегу `v*`. Не на каждый PR.
- **Кэш обязателен**: `Swatinem/rust-cache` для Cargo, кэш npm/pnpm. Без кэша одна
  Windows-сборка Tauri — 15–25 минут реального времени (= 30–50 минут лимита); с кэшем —
  заметно меньше. Сверить при первом запуске и записать в `docs/ci-budget.md`.
- **Ориентир расхода**: Linux CI ~3–5 мин на прогон; Windows-сборка ~10–15 мин с кэшем
  (×2 = 20–30 мин лимита). При ~20 PR и ~6 Windows-сборках в месяц — около 300 минут лимита,
  то есть 10% от 3000. Запас есть, но Windows-сборки «на каждый чих» его съедят.
- `concurrency` с `cancel-in-progress: true` в обоих workflow — старые прогоны по той же
  ветке отменяются.
- Тесты — по существу, не для галочки: логика денег, кэшбэка, траншей, импорта. UI-тесты —
  только на чистые функции (форматирование, парсинг ввода); e2e через `tauri-driver` — не в MVP
  (дорого по минутам, хрупко на Windows CI).
- Перед сжиганием минут локально/в облаке: `cargo test` и `vitest` должны быть зелёными до
  открытия PR.
